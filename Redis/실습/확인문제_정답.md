# Redis 입문 확인 문제 정답

학생이 먼저 자신의 말로 답한 뒤 확인할 수 있도록 배포 시점을 조절합니다.

## 1차시

1. 데이터를 주로 디스크보다 빠른 메모리에서 처리하기 때문입니다.
2. 복잡한 관계와 조회, 강한 영속성이 필요한 원본 데이터에는 관계형 DB가 더
   적합할 수 있기 때문입니다.
3. `PING`입니다.
4. `(nil)`이 반환됩니다.

## 2차시

1. `NX`는 키가 없을 때, `XX`는 키가 있을 때만 저장합니다.
2. 모든 키를 한 번에 찾는 동안 서버의 다른 요청을 지연시킬 수 있기 때문입니다.
3. 반환된 다음 커서가 `0`이면 끝입니다.
4. 키의 서비스, 대상, 식별자 영역을 알아보기 쉽게 구분하기 위해서입니다.

## 3차시

1. `-1`은 키가 있지만 만료 시간이 없고, `-2`는 키가 없다는 뜻입니다.
2. 적중은 Redis에 값이 있는 경우이고, 실패는 없어 원본을 조회해야 하는 경우입니다.
3. 변경 전 값이 사용자에게 반환되는 것을 막기 위해서입니다.
4. 오래된 데이터와 불필요한 데이터가 쌓여 메모리가 부족해질 수 있습니다.

## 4차시

1. 여러 키를 한 요청으로 조회해 네트워크 왕복을 줄이기 위해 사용합니다.
2. 서버에서 원자적으로 증가하므로 동시 요청에 의한 갱신 손실을 줄이기 때문입니다.
3. JSON을 읽고 파싱한 뒤 가격을 바꾸고 전체 JSON을 다시 저장해야 합니다.
4. 정수로 해석할 수 없다는 오류가 발생합니다.

## 5차시

1. 목록의 왼쪽, 즉 인덱스 `0`에서 보입니다.
2. `LTRIM key 0 9`를 사용합니다.
3. 목록에서 제거한 직후 처리가 끝나기 전에 장애가 나면 다시 꺼낼 수 없기 때문입니다.
4. 값이 들어올 때까지 시간 제한 없이 기다린다는 뜻입니다.

## 6차시

1. 한 번만 저장되며 두 번째 추가는 새 멤버 수 `0`을 반환합니다.
2. `SCARD`입니다.
3. `SINTER`입니다.
4. `SRANDMEMBER`는 값을 유지하고 `SPOP`은 값을 제거합니다.

## 7차시

1. Sorted Set은 각 멤버에 점수를 연결하고 점수 순서로 정렬합니다.
2. `ZRANGE key 0 9 REV WITHSCORES`입니다.
3. 사용자에게는 1등으로 표시합니다.
4. 새 항목을 만들지 않고 기존 멤버의 점수를 변경합니다.

## 8차시

1. `HMGET`입니다.
2. `HINCRBY key points 10`입니다.
3. 아니요. `user:7` Hash 키 전체에 적용됩니다.
4. 일반적으로 JSON String이 더 자연스럽습니다.

## 9차시

1. 고유 개수의 근사치만 보관하며 개별 방문자 목록을 제공하지 않기 때문입니다.
2. 안정적인 정수 식별자가 필요합니다.
3. Redis가 Stream 항목 ID를 자동 생성하라는 뜻입니다.
4. Geospatial 명령을 사용합니다.

## 10차시

1. Redis의 바이트 응답을 Python 문자열로 변환합니다.
2. JSON 등의 문자열 형식으로 직렬화해야 합니다.
3. 원본 DB 조회, Redis에 TTL과 함께 저장, 결과 반환 순서로 처리합니다.
4. 여러 명령의 네트워크 왕복 횟수를 줄이는 것입니다.

## 11차시

1. RDB는 특정 시점의 스냅샷, AOF는 데이터 변경 명령의 로그를 기록합니다.
2. 삭제나 잘못된 쓰기도 복제되며 과거 시점의 독립 사본을 보장하지 않기 때문입니다.
3. 제거할 키 없이 새 쓰기 명령에 오류를 반환합니다.
4. 인증되지 않은 접근, 데이터 유출, 데이터 삭제와 서버 악용 위험이 있기 때문입니다.

## 12차시

1. 조회수는 원자적 숫자 증가가 필요하고, 좋아요는 사용자 중복 방지가 필요하기
   때문입니다.
2. 중복 요청마다 인기 점수가 올라 실제 좋아요 수와 순위가 왜곡됩니다.
3. `cache:article:{id}` 키입니다.
4. 예시 답안: Redis가 캐시와 부가 기능이라면 원본 DB 기반 게시글 조회는 유지하고
   조회수·랭킹·최근 목록은 일시 중단하거나 지연 처리합니다. 실제 정책은 데이터의
   원본 위치와 장애 허용 범위에 따라 결정합니다.
