# 12차시. 종합 프로젝트

## 프로젝트 주제

**Redis 기반 실시간 인기 게시글 서비스**를 구현합니다. 지금까지 배운 자료구조를
하나의 기능에 억지로 모두 넣기보다, 각 요구사항에 가장 적합한 자료구조를 선택하는
것이 목표입니다.

## 학습 목표

- 요구사항을 Redis 키와 자료구조로 변환할 수 있습니다.
- Python으로 캐시, 조회수, 좋아요, 랭킹을 구현할 수 있습니다.
- 기능의 한계와 운영 시 고려사항을 설명할 수 있습니다.

## 1. 필수 요구사항

1. 게시글 정보를 저장하고 조회합니다.
2. 게시글 조회수를 원자적으로 증가시킵니다.
3. 사용자는 게시글에 한 번만 좋아요를 누를 수 있습니다.
4. 조회와 좋아요를 점수에 반영해 인기 게시글을 조회합니다.
5. 사용자별 최근 조회 게시글을 최대 5개까지 관리합니다.
6. 게시글 조회 결과는 60초 동안 캐시합니다.

## 2. 권장 키 설계

| 키 패턴 | 자료구조 | 용도 |
|---|---|---|
| `article:{id}` | Hash | 제목, 작성자, 내용 |
| `article:{id}:views` | String | 조회수 |
| `article:{id}:likes` | Set | 좋아요를 누른 사용자 |
| `ranking:articles` | Sorted Set | 인기 점수와 순위 |
| `user:{id}:recent-articles` | List | 최근 조회 게시글 |
| `cache:article:{id}` | String | JSON 조회 캐시 |

중괄호는 실제 키에 쓰는 문자가 아니라 바뀌는 식별자를 나타냅니다. 게시글 100의
실제 키는 `article:100`입니다.

## 3. 기능별 처리 흐름

### 게시글 조회

1. `cache:article:{id}`를 조회합니다.
2. 캐시가 없으면 원본 게시글을 읽고 60초 TTL로 저장합니다.
3. `article:{id}:views`를 1 증가시킵니다.
4. `ranking:articles`의 게시글 점수를 1 증가시킵니다.
5. 사용자 최근 조회 List의 왼쪽에 게시글 ID를 추가합니다.
6. `LTRIM`으로 최근 5개만 남깁니다.

### 좋아요

1. `SADD article:{id}:likes {user_id}`를 실행합니다.
2. 반환값이 `1`일 때만 새 좋아요입니다.
3. 새 좋아요일 때 랭킹 점수를 5 증가시킵니다.
4. 반환값이 `0`이면 이미 좋아요한 사용자이므로 점수를 변경하지 않습니다.

`SADD`의 반환값을 사용하면 중복 요청으로 랭킹 점수가 반복 증가하는 문제를 막을
수 있습니다.

## 4. CLI 프로토타입

```redis
HSET article:100 title "Redis 입문" author "민수" content "Redis를 배워 봅시다"
SET article:100:views 0

INCR article:100:views
ZINCRBY ranking:articles 1 article:100
LPUSH user:7:recent-articles 100
LTRIM user:7:recent-articles 0 4

SADD article:100:likes 7
SCARD article:100:likes
ZINCRBY ranking:articles 5 article:100

ZRANGE ranking:articles 0 9 REV WITHSCORES
```

CLI에서는 `SADD` 결과를 사람이 확인한 뒤 `ZINCRBY`를 실행합니다. Python
프로그램에서는 반환값을 조건문으로 검사해야 합니다.

## 5. 구현 순서

1. Redis 연결과 초기 게시글 데이터를 준비합니다.
2. `get_article`과 Cache-Aside를 구현합니다.
3. `view_article`에서 조회수, 랭킹, 최근 목록을 갱신합니다.
4. `like_article`에서 중복 좋아요를 막습니다.
5. `get_top_articles`에서 상위 게시글을 조회합니다.
6. 정상, 중복, 존재하지 않는 게시글을 테스트합니다.

## 6. 필수 테스트 시나리오

| 시나리오 | 예상 결과 |
|---|---|
| 같은 게시글을 두 번 조회 | 조회수와 랭킹 점수가 각각 2 증가 |
| 같은 사용자가 좋아요 두 번 요청 | 좋아요 수와 점수는 한 번만 증가 |
| 여섯 게시글을 차례로 조회 | 최근 목록에는 최신 5개만 존재 |
| 게시글을 처음 조회 | 캐시 실패 후 60초 TTL 캐시 생성 |
| 게시글을 다시 조회 | 캐시 적중 |
| 없는 게시글 조회 | 오류 또는 `None`, 잘못된 랭킹 생성 없음 |

## 7. 확장 과제

- 좋아요 취소 기능과 랭킹 점수 감소
- 날짜별 인기 게시글 랭킹
- Stream을 사용한 게시글 조회 이벤트 기록
- Pipeline으로 조회 시 여러 명령의 네트워크 왕복 줄이기
- 게시글 수정 시 캐시 무효화
- 비정상적으로 빠른 조회 증가를 막는 요청 제한

확장 과제에서는 기능 추가뿐 아니라 중복 요청, 부분 실패, 원본 DB와 Redis의
불일치가 어떤 결과를 만드는지도 설명합니다.

## 전체 과정 정리

- 키 이름과 TTL도 데이터 설계의 일부입니다.
- 자료구조는 저장할 값보다 해결할 질문을 기준으로 선택합니다.
- Redis는 매우 빠르지만 메모리, 장애, 일관성, 보안을 자동으로 해결하지 않습니다.
- 작은 기능부터 구현하고 측정한 뒤 운영 요구에 맞게 확장합니다.
