# 11차시. 운영 기초

## 학습 목표

- RDB와 AOF 영속성 방식의 차이를 설명할 수 있습니다.
- 메모리 한도와 제거 정책의 의미를 설명할 수 있습니다.
- 복제, 보안, 모니터링의 기본 점검 항목을 나열할 수 있습니다.

> 이 차시의 설정 변경 명령은 개인 실습 서버에서만 실행합니다. 공유 서버나
> 운영 서버의 설정은 담당자와 배포 절차를 통해 변경해야 합니다.

## 1. 영속성

Redis는 주로 메모리에서 동작하지만 데이터를 디스크에 남길 수 있습니다.

### RDB 스냅샷

특정 시점의 메모리 데이터를 하나의 스냅샷 파일로 저장합니다.

- 파일이 비교적 작고 백업과 재시작이 빠릅니다.
- 마지막 스냅샷 뒤의 변경 내용은 장애 시 잃을 수 있습니다.

### AOF

데이터를 변경한 명령을 로그 형태로 기록하고 재시작할 때 다시 적용합니다.

- 기록 주기에 따라 데이터 손실 범위를 줄일 수 있습니다.
- 파일 크기와 쓰기 비용, 재작성 정책을 관리해야 합니다.

### 선택 질문

- 이 Redis 데이터는 원본인가, 다시 만들 수 있는 캐시인가?
- 장애 시 몇 초 또는 몇 분의 데이터 손실을 허용할 수 있는가?
- 복구 시간 목표는 얼마인가?
- 백업 파일을 실제로 복원해 보았는가?

설정을 조회합니다.

```redis
CONFIG GET save
CONFIG GET appendonly
LASTSAVE
```

## 2. 메모리 관리

```redis
INFO memory
CONFIG GET maxmemory
CONFIG GET maxmemory-policy
```

`maxmemory`는 Redis가 사용할 메모리 한도이며, 한도에 도달했을 때 어떤 키를
제거할지 `maxmemory-policy`가 결정합니다.

| 정책 계열 | 의미 |
|---|---|
| `noeviction` | 기존 키를 제거하지 않고 새 쓰기에 오류 반환 |
| `allkeys-*` | 모든 키 중 정책에 따라 제거 |
| `volatile-*` | TTL이 설정된 키 중 정책에 따라 제거 |

LRU는 최근 사용 정도, LFU는 사용 빈도를 근사하여 제거 대상을 고릅니다. 캐시
서버에는 `allkeys-lru`나 `allkeys-lfu`를 검토할 수 있고, 중요한 원본 데이터가
있다면 자동 제거가 적합한지 먼저 판단해야 합니다.

## 3. 복제와 고가용성

복제본은 기본 서버의 데이터를 따라가며 읽기 확장이나 장애 대응에 활용됩니다.

```redis
INFO replication
ROLE
```

- 복제는 일반적으로 비동기이므로 장애 직전 쓰기가 복제본에 도달하지 않을 수 있습니다.
- 복제는 백업을 대신하지 않습니다. 실수로 삭제한 데이터도 복제될 수 있습니다.
- Sentinel은 장애 감지와 자동 전환을 지원합니다.
- Cluster는 데이터를 여러 노드에 분산하여 용량과 처리량을 확장합니다.

입문 단계에서는 각 기술의 목적을 구분하고, 실제 도입 시 운영 복잡성과 장애
시나리오를 별도로 학습합니다.

## 4. 보안 기본 원칙

1. Redis 포트를 공용 인터넷에 직접 노출하지 않습니다.
2. 방화벽과 사설 네트워크로 접근 대상을 제한합니다.
3. ACL로 사용자별 명령과 키 접근 권한을 최소화합니다.
4. 전송 구간 암호화가 필요하면 TLS를 구성합니다.
5. 비밀번호를 코드와 저장소에 기록하지 않습니다.
6. 위험한 관리 명령의 사용 권한을 제한합니다.

현재 접속 사용자를 확인합니다.

```redis
ACL WHOAMI
ACL LIST
```

`ACL LIST` 결과에는 보안 설정 정보가 포함될 수 있으므로 외부에 그대로 공유하지
않습니다. 실무에서는 애플리케이션마다 필요한 키 패턴과 명령만 허용합니다.

## 5. 관측과 문제 확인

```redis
INFO stats
INFO clients
INFO memory
SLOWLOG LEN
SLOWLOG GET 10
CLIENT LIST
```

주요 관측 항목은 다음과 같습니다.

- 사용 메모리와 메모리 한도
- 초당 명령 처리량
- 연결 수와 거부된 연결
- 캐시 적중과 실패
- 제거된 키와 만료된 키
- 복제 지연과 연결 상태
- 느린 명령과 응답 지연

`MONITOR`는 모든 명령을 실시간으로 보여 주지만 서버 부하와 민감정보 노출 위험이
있으므로 운영 환경에서 상시 사용하지 않습니다.

## 실습. 서버 건강 점검표

개인 서버에서 다음 항목을 확인하고 값을 기록합니다.

| 항목 | 확인 명령 | 내 서버 결과 |
|---|---|---|
| Redis 버전 | `INFO server` | |
| 사용 메모리 | `INFO memory` | |
| 연결 클라이언트 수 | `INFO clients` | |
| 영속성 설정 | `INFO persistence` | |
| 복제 역할 | `ROLE` | |
| 메모리 제거 정책 | `CONFIG GET maxmemory-policy` | |
| 느린 명령 수 | `SLOWLOG LEN` | |

## 확인 문제

1. RDB와 AOF의 기록 방식은 어떻게 다른가요?
2. 복제가 백업을 대신할 수 없는 이유는 무엇인가요?
3. `noeviction` 정책에서 메모리 한도에 도달하면 어떻게 되나요?
4. Redis 포트를 인터넷에 직접 노출하면 안 되는 이유는 무엇인가요?

## 정리

- 영속성은 허용 가능한 데이터 손실과 복구 시간을 기준으로 선택합니다.
- 메모리 한도와 제거 정책은 Redis의 용도에 맞게 함께 설정합니다.
- 복제, 백업, 보안, 모니터링은 서로 다른 운영 문제를 해결합니다.
